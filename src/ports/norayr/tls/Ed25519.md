# Ed25519 signatures

`TLSEd25519` provides deterministic Ed25519 public-key derivation, signing and
verification in Oberon, using SHA-512 and 32-bit integer arithmetic. It implements
the pure Ed25519 mode of [RFC 8032](https://www.rfc-editor.org/rfc/rfc8032).
`TLSEd25519Keys` generates seeds using the existing Linux `TLS13Random` entropy
wrapper. The bundled networking package builds these modules in model 2 on Linux.

## API

All procedures return `BOOLEAN`. Byte arrays are `ARRAY OF CHAR`, passed by `VAR`
to avoid input copies. Inputs are read-only unless they alias an output.

| Procedure | Inputs and output |
| --- | --- |
| `TLSEd25519.PublicKey(seed, publicKey)` | Exactly 32 seed bytes; writes the first 32 public-key bytes. |
| `TLSEd25519.Sign(seed, message, offset, count, signature)` | Exactly 32 seed bytes; signs the selected message range and writes the first 64 signature bytes. |
| `TLSEd25519.Verify(publicKey, message, offset, count, signature)` | Exactly 32 public-key bytes and exactly 64 signature bytes; verifies the selected message range. |
| `TLSEd25519Keys.Generate(seed, publicKey)` | Distinct output arrays, each exactly 32 bytes; writes a fresh seed and its public key. |

For example, with `seed` and `publicKey` declared as `ARRAY 32 OF CHAR`, and
`signature` as `ARRAY 64 OF CHAR`:

```oberon
IF TLSEd25519Keys.Generate(seed, publicKey) THEN
  IF TLSEd25519.Sign(seed, message, 0, length, signature) THEN
    valid := TLSEd25519.Verify(publicKey, message, 0, length, signature)
  END
END
```

`offset` and `count` must be nonnegative and select bytes within the message
array. Empty ranges, including one at the end of the array, are accepted.
Signing and verification use fixed-size working storage, with no 32 KiB message
limit or message-sized allocation. Signing hashes the message twice, so callers
must keep its contents unchanged throughout the call.

The core procedures leave outputs unchanged on failure and preserve bytes beyond
the required output length. `Generate` instead clears both entire output arrays
on failure, including invalid lengths, aliased outputs and entropy-read failures.
The seed is secret key material: retain it securely and never publish it.

## Verification policy

Verification requires canonical encodings of the public key A, nonce point R and
scalar S, with S smaller than the group order. Both A and R must be nonidentity
points in the prime-order subgroup. It checks the uncofactored equation
`[S]B = R + [H(R || A || message)]A`. This deliberately rejects low-order and
mixed-order points, including cases accepted by cofactored verification.

The API signs the supplied bytes exactly. Protocols must define a stable encoding
and domain separation for the data they sign. Ed25519ctx and Ed25519ph require
their own algorithms; hashing a message before calling `Sign` still uses pure
Ed25519 on those hash bytes.

## Incremental SHA-512

`TLSSHA512.Context` supports hashing byte ranges without a bounded buffer:

1. Call `Init512(context)` before use or reuse.
2. Call `Update(context, data, offset, count)` for each range.
3. Call `Final512(context, digest)` with room for at least 64 bytes.

Rejected ranges and short digest outputs leave the initialized context unchanged.
Successful finalization writes 64 bytes and clears and consumes the context;
subsequent updates or finalization fail until reinitialization. `Digest512` and
`Digest384` retain their existing `TLSBytes.Buffer` interfaces.

## Provenance and validation

The field representation follows `TLSX25519` and the public-domain NaCl reference;
Edwards point formulas and scalar multiplication follow
[TweetNaCl](https://tweetnacl.cr.yp.to/20140427/tweetnacl.c). Constants and the signing
construction follow RFC 8032. The modules are licensed LGPL-3.0-or-later.

`TLSTestEd25519` covers RFC vectors and API checks. `TLSTestSHA512Stream` covers
incremental hashing and lifecycle checks. Both run in the normal TLS test suite.
An additional driver uses Python `cryptography` and `hashlib` for independent
comparisons, long messages, malformed encodings, subgroup checks and a partial
entropy-read failure:

```sh
OBERON=/usr/share/voc/2/sym python3 src/test/ports/tls/ed25519.py \
  /usr/bin/voc build/tests/ed25519 2 -sm
```

Use the symbol directory matching the selected compiler/runtime. The driver
compiles the local crypto sources into its build directory and requires the
Python `cryptography` package.

Secret scalar multiplication uses fixed loop bounds and no secret-indexed
tables. The arithmetic, compiler output and memory erasure have not been
independently security-audited. Constant-time execution and reliable erasure of
all intermediate secrets are not guaranteed. Functional and sanitizer tests do
not establish resistance to side-channel attacks.
